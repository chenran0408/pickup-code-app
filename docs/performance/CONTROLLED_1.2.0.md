# 1.2.0 同机性能对照

测试日期：2026-10-03。基线 `407ca98`（UI 优化前），候选 `2faf6eb`（UI 优化后）。均为 1.2.0 / 28、DB9、arm64 Release，使用相同调试签名、R8、资源裁剪及原生库压缩。正式 APK 使用 fork 独立密钥。

## 条件与方法

- 手机：小米 2410DPN6CC，Android 17 / API37，1440×3200，density600，字体1.0，跟随系统主题；USB 供电，电池温度33.2–34.0°C。帧记录显示约16.63ms的帧间隔，未强改刷新率。
- 数据：144条合成记录（120活跃、24已取、12站点），两版沿用同一数据库与设置。原有6条归档记录未修改。无图片、网络请求或实时消息注入。
- 顺序 ABBA：安装保留数据，每组显式 AOT `speed`，两次预热，5次 `am start -S -W` 进程冷启动，3轮滚动。每版10次启动、6轮滚动。
- 每轮滚动重新启动并预热字形/品牌绘制，再清零 `gfxinfo`；执行6次向下、6次向上350ms滑动，坐标固定(720,2500)↔(720,900)，收集 `dumpsys gfxinfo ... framestats`。
- 首帧来自 `TotalTime`，不是整个列表可用时间；文件缓存不清空。滚动P95/P99为每轮百分位的中位数，jank率按总帧数加权。

## 结果

| 指标 | 基线 | 优化后 |
|---|---:|---:|
| 进程冷启动首帧中位数 | 111ms | 113ms |
| 首帧范围（10次） | 106–117ms | 105–125ms |
| 滚动采样总帧数 | 3,890 | 3,810 |
| 滚动P95中位数 | 16ms | 16ms |
| 滚动P99中位数 | 18ms | 18ms |
| 系统现代jank计数 | 0 | 0 |
| legacy jank帧/比例 | 36 / 0.925% | 36 / 0.945% |

此场景两版表现相近，未观察到明确的流畅度提升或明显退化。首帧中位数相差2ms，样本范围重叠；不宣传提速百分比。收益主要是操作更直接、减少主线程列表计算与后台页面工作。

## 复现

使用两个已知提交的同配置 Release APK，先在debug安装包运行受 `android.permission.DUMP` 保护的 `PerformanceFixtureActivity`，以 `--es action seed` 生成合成记录；执行：

```text
python tools/performance_compare.py --serial <设备ID> --baseline <基线APK> --candidate <候选APK> --output <本地结果目录>
```

之后安装debug包，以 `--es action clean` 仅清理本工具创建且未被编辑的记录，并核对状态文件 `files/performance-fixture-status.json`。工具只存在于debug源集，正式APK不包含。

完整样本与APK哈希见 [results-1.2.0.json](results-1.2.0.json)。原始帧日志保存在本地交付目录。单设备、固定AOT、不同首页布局限制见JSON；系统0 jank计数不意味着完全没有卡顿。真实短信/微信通知、低版本设备、首次安装和网络AI仍须单独验证。
